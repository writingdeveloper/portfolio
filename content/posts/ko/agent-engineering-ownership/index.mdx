이제 코딩 AI를 주로 자동완성처럼 쓰지는 않습니다. 범위가 정해진 작업을 에이전트에게 주고, 저장소를 직접 조사하게 한 뒤 여러 파일에 걸쳐 구현하고 검증하게 하는 경우가 더 많습니다.

겉으로 보면 엔지니어링 자체를 위임하는 것처럼 보입니다. 제가 중요하게 보는 구분은 **무엇을 위임하느냐**입니다.

구현은 위임할 수 있습니다. 소유권은 위임하지 않습니다.

## 작업의 단위가 커졌습니다

예전에는 함수나 파일 하나가 AI에게 맡기기 좋은 단위였다면, 지금은 Claude Code나 Codex에게 오류 원인을 추적하고, 여러 레이어를 수정하고, 회귀 테스트를 추가하고, 필요한 게이트까지 실행하게 하는 일이 흔합니다.

그러면 병목도 달라집니다. 타이핑보다 아래 문제가 더 중요해집니다.

- 작업 경계를 어디까지 둘지,
- source of truth가 무엇인지,
- 어떤 증거를 완료로 인정할지,
- 모델 오류와 시스템 오류를 어떻게 분리할지,
- 그럴듯한 결과가 바로 릴리스가 되지 않게 어떻게 막을지.

최근 프로젝트들은 점점 이 경계를 중심으로 설계하고 있습니다.

## DevDeck: 병렬 에이전트에는 상태 소유권이 필요합니다

[DevDeck](/projects/devdeck)은 여러 저장소의 코딩 세션을 놓치지 않기 위한 도구로 시작했고, 지금은 Claude Code·Codex·Antigravity 세션을 다루는 local-first control plane에 가깝습니다.

어려운 문제는 터미널을 더 많이 그리는 것이 아니었습니다. 공유 상태를 누가 소유하는지 정하는 일이었습니다.

한 머신에서 세션 제목을 바꿨다고 그 renderer가 보여주는 값이 곧 진실이 되어서는 안 됩니다. host가 쓰기를 소유하고, 디스크에 저장하고, 성공을 응답하고, 다른 observer들이 같은 결과로 수렴해야 합니다. 실패·재연결·stale response·재시작이 있어도 이 규칙이 유지돼야 합니다.

1.37.7 검토에는 **1,257개 통과·1개 생략**, 2026-09-08 유지보수 후보 기록에는 **1,289개 통과·1개 생략**이 있습니다. 서로 다른 버전의 과거 검증 기록이며 현재 실행한 테스트 수가 아닙니다. 이후 동기화 작업은 소스·패키지 게이트를 별도로 유지하고, 자동 검사를 사람의 시각 검수나 장기간 물리 네트워크 검증과 동일시하지 않습니다.

숫자 자체보다 중요한 것은 그 테스트가 에이전트 작업의 **소유권 규칙**을 지키고 있다는 점입니다.

## studios: 생성과 검수는 같은 책임이 아닙니다

[studios](/studio)는 이미지·영상·3D·음성·음악 생성을 MCP 툴로 노출합니다.

파이프라인의 책임을 일부러 나눴습니다.

1. 툴이 생성하고,
2. 기계 게이트가 명백한 실패를 제거하고,
3. 호출한 에이전트가 결과물을 직접 보고,
4. 판정과 이유를 자산과 함께 저장합니다.

생성기가 자기 결과를 스스로 합격시키지 못하게 한 것입니다.

이 구조는 특정 모델보다 오래 갈 수 있다고 봅니다. 모델은 바뀌어도 품질 경계가 관찰 가능하게 남는 파이프라인은 유지할 수 있습니다.

## Creator Learning OS: 미완료는 승인으로 해석하지 않습니다

Creator Learning OS는 채널 데이터를 한 가지 구체적인 다음 행동으로 바꾸는 상용 SaaS 방향으로 개발하고 있습니다.

릴리스 판정은 의도적으로 보수적으로 만들고 있습니다. 고객 OAuth, 결제, provider readiness, 영속 DB, 백업·복구는 마케팅 체크박스가 아닙니다. 프로덕션 의존성이 빠져 있으면 readiness가 fail-closed 해야 합니다.

에이전트가 불완전한 검사를 승인으로 재해석하는 것보다 시스템이 **아직 준비되지 않음**이라고 말하는 편이 낫습니다.

AI 기능의 eval도 마찬가지입니다. 실패했을 때 실제로 막히는 것이 있어야 평가가 의미를 가집니다.

## 멀티 에이전트보다 먼저 git worktree

여러 에이전트를 병렬로 돌릴 때는 하나의 checkout을 공유시키기보다 격리된 git worktree를 선호합니다.

규칙은 단순합니다.

- 작업 하나당 worktree 하나,
- 명시적인 acceptance criteria,
- 작업별 테스트,
- diff 검수,
- gate 통과 후에만 통합.

복잡한 multi-agent 연구라기보다 기존 소프트웨어 격리 원칙을 에이전트에 적용한 것입니다. 그래서 오히려 안정적으로 작동합니다.

## 여전히 사람이 소유하는 것

에이전트를 많이 사용하지만 아래 경계는 흐리지 않으려고 합니다.

- 아키텍처와 되돌리기 어려운 제품 결정,
- 어떤 증거면 충분한지,
- 보안·프라이버시 trade-off,
- 실패한 게이트를 예외 처리할 수 있는지,
- 최종 릴리스 결정.

목표는 AI가 작성한 코드 비율을 최대화하는 것이 아닙니다.

문제가 생겼을 때 더 쉽게 추적할 수 있는 상태를 유지하면서, 한 사람이 안전하게 감독할 수 있는 유용한 작업량을 늘리는 것이 목표입니다.

현재 제 작업은 점점 **모델 주변의 agent systems, tool use, evals, state, observability, production reliability** 쪽으로 모이고 있습니다.
